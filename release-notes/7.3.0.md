# 7.3.0

## What changed

- `npm run check:config` / `node index.js --check-config`: a dry run that validates a member host
  without a share. It checks the runtime and configuration shape, that the signing key parses and
  is on `<member>@<permission>` on chain, the API node (reachable, synced, right chain id), the
  contract's active key (fingerprint printed), the `oracles.a` row and index, CPU/NET headroom
  and `DB_FILE` writability; with `SHARE_KEY_*` staged it runs the same share consistency check
  the boot self-check runs. It starts nothing, pushes nothing and prints no secret. Exit 0 means
  nothing it saw would stop the service.
- Operator guide: the mainnet chain id was wrong (`…aec5a4`; the chain reports `…aea5a4`), found by
  the first live run of the dry run. Corrected. Sections 3, 4, 5 and 7 describe the dry run.
- The service itself is unchanged: no poller, signing, combine or chain-action code was touched.

## Why

- Community operators preparing hosts for the member handover cannot use `READONLY_MODE` to try a
  host before the key ceremony: the boot self-check is fail-closed and exits without a share the
  chain knows. The dry run gives them a truthful answer at that stage.
- A member configured from the guide's old chain id would have had every transaction rejected.

## Deploying

Nothing in this release changes member behaviour. Roll it like any other: one member at a time,
and promote the next only after the previous one shows `/health-check` `bootCheck.ok: true`,
`/version` `7.3.0`, and `submitpart` + `setrand` on chain. Operators may run
`npm run check:config` on the new checkout before restarting.
