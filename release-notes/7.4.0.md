# 7.4.0

## What changed

- `node index.js --check-config --proposal <proposer>/<name>` (also `npm run check:config --
  --proposal …` or `CHECK_PROPOSAL=…`): the dry run now reads the pending `eosio.msig` proposal that
  will switch the key and the member list, decodes it with the contract ABI, and checks it against
  this host: the proposed key's version, size and fingerprint against the staged
  `SHARE_KEY_PUBLIC_KEY_N`, the full share consistency check against the proposed modulus, and
  that your account sits at `SHARE_KEY_SHARE_INDEX` in the proposed member list. A share that does
  not match the active key but matches the proposed one is reported as a warning instead of a
  failure, so a correctly staged member exits 0 while it waits in its expected crash loop.
- Operator guide 4.1 "Validating a staged member before the switch": how to run the dry run with
  the unit's own environment file through `systemd-run`, which lines of the pre-switch report prove
  what, why the secrets belong in the 0600 environment file rather than `Environment=` lines of
  the unit, and the `--proposal` check. Sections 6.2 and 7 point to it.
- The service itself is unchanged: no poller, signing, combine or chain-action code was touched.

## Why

- A member staged for a planned key switch runs in an `ORACLE_NOT_REGISTERED` crash loop until the
  producers execute the switch. That loop proves the process starts and reaches the chain, not that
  the share is for the key being installed or that the index matches the new member list. Operators
  asked for a check that answers exactly that before the switch, without starting anything.
- `npm run check:config` from a shell does not see the systemd unit's `EnvironmentFile`, so an
  operator who configures the service only through the unit could not run the dry run at all.

## Deploying

Nothing in this release changes member behaviour. A member staged for a switch may update its
checkout to 7.4.0 before the switch and keep the same crash-loop expectation (the boot self-check
is unchanged); or stay on 7.3.0 and run the proposal check from a 7.4.0 checkout elsewhere, with
the same environment file. For a running member, roll it like any other: one at a time, and
promote the next only after the previous one shows `/health-check` `bootCheck.ok: true`,
`/version` `7.4.0`, and `submitpart` + `setrand` on chain.
