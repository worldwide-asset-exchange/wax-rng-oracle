# 7.5.0

## What changed

- A `setrand` the API node refuses to carry is no longer treated as a delivery failure. The
  poller classifies the rejection first: only a failure inside contract code (the dApp's callback
  asserted, aborted, is missing, or faulted — nodeos `action_validate` / `wasm` exception families)
  pushes `markfailed` with the computed signature. `tx_cpu_usage_exceeded` (including the
  subjective `exceeded failure limit for account <member>`), `tx_net_usage_exceeded`,
  `actor_whitelist_exception`, expiry and HTTP errors are logged as `API node rejected setrand
  (<exception>)`, counted as `setrand_rejected`, alerted (one post a minute), and retried with the
  usual back-off — four attempts over about four seconds, after which the member leaves that
  request to the other two.
- A rejected transaction push is no longer re-sent. The RPC retry wrapper used to re-push every
  non-2xx response up to five times, so one lost `setrand` race counted as five failures on a node
  that bills subjectively. Reads keep the retry.
- `setrand` outcomes the contract refuses for a state reason (`paused`, `key retired`, result
  already parked, `no request found`) are counted as `job_collision` / `execute_skipped` instead of
  as deliveries.
- A port already in use is fatal and logged (`HTTP API cannot listen on port <n> (EADDRINUSE)`,
  exit 1) instead of leaving a member signing with no `/health-check` and no explanation.
- `/health-check` carries `headBlockLagSeconds`, the age of the API node's head block; the status
  code is unchanged. Alert on it host-side (guide 6.4).
- Log lines carry ANSI colour only on a terminal (`logger.color` / `LOGGER_COLOR` overrides).
- Operator guide: what the push node must look like (no `actor-whitelist`,
  `disable-subjective-api-billing = true`, synced), NET sizing from mainnet measurements, the
  `useradd` step and systemd fast-exit codes, log-to-file recipes, and the new metric, field,
  alerts and troubleshooting rows.

## Why

- In the three days after the 2026-11-13 key switch the three members pushed 184 `markfailed`
  (1.25 % of 14,695 requests), against none in the three days before. Every stored
  `error_message` was one of two node-side refusals — a subjective failure limit tripped by lost
  `setrand` races (166) and an actor whitelist on one member's node that excluded `orng.wax` (18)
  — and none a dApp failure. Each parked a deliverable result in `undelivered1` until a
  `retrydeliver`, so dApps got their numbers late, and the stored messages pointed operators at the
  dApp instead of at their own node. The five-fold re-push of every lost race is what made the
  failure limit trip in the first place.
- Two operators hit the silent port collision and the missing service user while bringing their
  members up on the switch day; one signed nothing for ten minutes behind a lagging node while
  `/health-check` said 200.

## Deploying

No chain action, byte format or configuration key changes; `LOGGER_COLOR` is new and optional.
Roll one member at a time and promote the next only after the previous one shows `/health-check`
`bootCheck.ok: true` with a `headBlockLagSeconds` of a few seconds, `/version` `7.5.0`, and
`submitpart` + `setrand` on chain. Members whose push node bills subjectively or whitelists actors
will see `setrand_rejected` climb where they used to see `markfailed`; the fix for that is on the
node (guide 6.6, 7), not in the process.
