# v6.1.0 (unreleased — WBP-2067)

Security-hardening release of the `orng.wax` threshold member. Full detail in
[`CHANGELOG.md`](../CHANGELOG.md) §6.1.0; this file is the operator view.

## What an operator sees

- **A member with a wrong / mismatched share or index no longer starts.** On boot it checks its
  share against the on-chain `pubkeys` row for the active version and its configured share index
  against `oracles.a[<nodeOwner>].oracle_index`, and exits 1 on any failed check, logging
  `Boot self-check FAILED: … (<CODE>)` / `… failed checks: <names>` (names only, never values).
  Expect a visible crash loop instead of a member that signs and fails every combine. If the chain
  RPC is down (or a node is still replaying) at boot it retries for about a minute
  (`BOOT_CHECK_RPC_RETRIES` × `BOOT_CHECK_RPC_RETRY_BASE_MS`) and then exits 1 as well — the restart
  is the retry. This applies to `READONLY_MODE` replicas too.
- **Requests of another key version are skipped**, not signed: after a `setpubkey` rotation the
  members must be re-keyed and restarted (the log says so once per version;
  `key_version_skipped` metric).
- **`/health-check` carries `bootCheck`** (`ran`, `ok`, `rpcReachable`, `activeKeyFound`,
  `oracleIndexMatches`, `shareConsistent`, `activeVer`) and returns 500 unless the check passed.
- **A poisoned partial on chain no longer stalls a request.** The combine skips zero / out-of-range /
  malformed partials and tries k-subsets; the member logs `Combine diagnostics {…rejectedShares,
  failedSubsets, suspectShareIndices…}` with the job id and its own oracle index, and emits
  `combine_rejected_part{idx}` / `combine_suspect_share{idx}` / `combine_failed{code}` metrics. A job
  whose parts genuinely cannot combine is parked until its on-chain parts change (`… parked until
  parts change` in the log) rather than retried identically. The matching Slack alert is throttled
  to one per minute per member, with a suppressed count.
- **`/version` reports `6.1.0`** — the package version and the release tag are one scheme from now on
  (see `CHANGELOG.md` → *Version scheme*). It reported `7.1.4` on the v6.0.0 image.
- **`NODE_ENV=production` is baked into the image**; the infra env still sets it too. The process
  refuses `NODE_ENV=test`.

## What did NOT change

- The bytes on chain: `submitpart sig_i` (unpadded lower-case hex of the partial) and
  `setrand`/`markfailed sig` (lower-case hex, exactly modulus width, < n) are identical to v6.0.0.
  The signing library's 2.0.0 release replays 1.3.0 golden vectors bit-for-bit.
- Key material handling, env variable names, the HTTP routes, the poll intervals, and the back-off
  policy for RPC/delivery failures.
- The image's runtime (`node:20-bookworm`, `node index.js`, non-root `node`).

## Release mechanics

- Tag `v6.1.0` on the release branch after merge (the GitLab gate accepts exactly `v6.1.0`, `v6.0.1`
  or `v7.0.0` over `v6.0.0`). **Not tagged by WBP-2067.**
- All three members move together (one image, three overlays, digest-pinned by the pipeline).
- Dependency floors are enforced three times: `check_deps_and_unit_tests` (GitLab `gate` stage),
  the GitHub workflow, and `RUN node scripts/check-dep-floors.js` inside `Dockerfile_eks`.
